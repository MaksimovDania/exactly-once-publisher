# Ревью решения: публикация 200k статей в день

Проверял скептически: читал код, гонял chaos-тест с вариациями и мутациями в копии, а самые важные утверждения проверял на **настоящем WordPress 7.1.3** в Docker. Исходные файлы в `hw/` не менялись.

**Коротко.** Архитектура выбрана верно: Postgres как очередь, аренда сайта, черновик плюс CAS по `step`. Ядро гарантии держится: ни в одном из 13 прогонов с хаосом (до 67 SIGKILL, 16 заморозок, 50% сбоев API, 42 обрыва соединений с БД) не было двойной или пропущенной публикации. Но два утверждения в документах на практике неверны:

1. «Лишний черновик безвреден». На WordPress он занимает slug, и статья выходит по адресу `slug-2`. Воспроизведено 5 из 5 раз.
2. «Восстановление БД из бэкапа не приведёт к повторной публикации». В трёх из четырёх реалистичных вариантов получается дубль.

Плюс несколько багов поменьше и неточности в таблице платформ (Webflow, Wix).

## 1. Вердикты по архитектурным решениям

### 1.1 Postgres как очередь, стейт-машина и локи: **верно**

- **Нагрузка.** 2,3 статьи/с в среднем, около 25 в пике, примерно 150 записей/с в БД. Для `SKIP LOCKED` это ничтожно: Oban, River, graphile-worker и solid_queue держат на порядки больше.
- **Что выигрываем.** Задача и её состояние живут в одной строке. Поэтому нет ни dual write, ни outbox, а `ON CONFLICT DO NOTHING` даёт идемпотентный enqueue бесплатно. Это главный аргумент, и он верный: Kafka, SQS или RabbitMQ всё равно потребовали бы хранить шаги в БД.
- **Что теряем.** Встроенный DLQ, fan-out событий другим потребителям, push вместо поллинга. Для этой задачи это не важно.
- **Производительность LEASE_SITE.** Я её измерил (`bench_lease.py`): 1,6 мс на 100k простаивающих сайтов и 1M строк истории; 7 мс при 1 000 сайтов с бэклогом; 31 мс при 50 000 сайтов с бэклогом. Планировщик делает hash semi-join по частичному индексу, а не обходит простаивающие сайты по одному. Значит, оговорка `ponytail` про ~100k сайтов честная, а до 100k запас есть.
- **Где выбор перестаёт работать.** Не столько в пропускной способности, сколько в соединениях: одна лейна держит одно соединение даже пока ждёт HTTP. Я упёрся в это вживую. Шесть параллельных прогонов по 4 × 8 лейн дали `too many clients` при `max_connections=100`, после чего лейны переподключались каждую секунду без backoff: 5 858 неудачных подключений в логах. На ×100 (тысячи лейн) нужны пул, PgBouncer и NOTIFY вместо поллинга; README это и предлагает.
- **Более стандартный вариант.** Ближайший управляемый аналог аренды сайта — SQS FIFO с `MessageGroupId = site`: одно сообщение в полёте на группу. Но он возвращает dual write. Готовые Python-библиотеки очередей на Postgres (procrastinate, pgqueuer) не умеют аренду по ключу с обходом по кругу. Значит, своя реализация на ~150 строк оправдана.

### 1.2 Аренда сайта, а не статьи: **верно с оговорками**

Идея правильная: один писатель на сайт снимает проблему «все воркеры навалились на один горячий сайт» без распределённого лимитера. Оговорки:

- **Лимиты не всегда на сайт.**
  - Webflow считает лимиты **на API key**, а не на сайт ([rate limits](https://developers.webflow.com/data/reference/rate-limits)). Если один OAuth-токен клиента авторизован на несколько сайтов, локальный темп по сайту превысит общий лимит.
  - У WordPress лимиты ставит хостинг или WAF, часто по IP и общие для многих клиентов одного хостинга (WP Engine, Cloudflare).
  - У Wix масштаб лимитов не задокументирован.
  - README предусматривает лимит на приложение целиком, но Webflow уже сейчас ближе к этому случаю, чем к лимиту на сайт.
- **Аргумент про гонку refresh-токенов слабее, чем подан.**
  - У четырёх названных платформ ротации refresh-токенов по сути нет: application passwords в WP; токены Webflow не истекают; в текущем OAuth Wix токен выдаётся по client credentials на 4 часа без refresh-токена ([Wix OAuth](https://dev.wix.com/docs/build-apps/develop-your-app/access/authentication/authenticate-using-oauth.md)).
  - Аренда не даёт взаимного исключения: зомби может обновлять токен одновременно с новым владельцем. Если refresh когда-то понадобится, его надо делать под CAS в БД, а не полагаться на аренду.
- **Аренда может истечь посреди одной статьи.**
  - Аренда не продлевается (60 с). `SLICE` проверяется только между статьями.
  - httpx `timeout=15` — это таймаут на операцию, а не на запрос целиком.
  - Худший случай одной статьи: 2 запроса media + 2 draft + 1 publish по 15 с, итого ≥75 с, а медленная по байту отдача ещё дольше.
  - Тогда сайт берёт вторая лейна: темп удваивается, и возможна гонка за ту же статью. Корректность держит CAS, но на WP это порождает лишний черновик, то есть баг B1.
- **Потолок на сайт и HOL.**
  - Сайт обслуживается последовательно, поэтому его потолок задаёт задержка ответа (около 2 с на статью), а не лимит платформы. Shopify Plus допускает 1000 очков/с, но мы его не используем.
  - SLO «due-статья live за 15 мин» недостижим для клиента с 5 000 статей на одном сайте в 09:00 (около 2,8 ч при 2 запросах/с). SLO надо формулировать относительно пропускной способности сайта.
  - Масштабировать воркеры по «возрасту старейшей due-статьи» в этом случае бесполезно: лишние воркеры не помогут одному сайту.
- **Справедливость на уровне сайта, а не клиента.** Клиент с 1 000 сайтов получает в 1 000 раз большую долю.
- **Задержка до 60 с после kill -9** допустима при SLO в 15 минут. SIGTERM я проверил отдельно: процесс вышел через 0,44 с, все сайты отпущены, на полпути ни одной статьи.

### 1.3 Аргумент exactly-once: **верно для основного пути, неверно в двух заявленных местах**

Что действительно держит гарантию: черновик + CAS по `step` + publish только по id из БД. Это подтверждают мутации. Без поиска по маркеру ни одна статья не вышла дважды, только лишних черновиков стало 33. Поиск нужен не для того, чтобы не было двух live-постов, а для чистоты URL на WP, для бэкапа и для платформ без черновиков. Сбой коммита в БД с неясным исходом тоже безопасен: шаг либо закоммичен, либо повторяется, а публикуется только закоммиченный id. Это подтвердил прогон с `pg_terminate_backend`.

Дыры:

| направление | результат |
|---|---|
| лишний черновик (зомби или поиск его ещё не видит) | **ломается на WP**, баг B1: статья выходит на `slug-2` |
| бэкап БД | **ломается** в 3 из 4 вариантов, баг B2 |
| маркер вырезается или санитизируется | WP: kses сохраняет `<!-- ryze:uuid -->` даже для роли author без `unfiltered_html` (проверено). **Wix**: контент в формате Ricos JSON, HTML-комментарию просто некуда встать. Webflow RichText: не задокументировано, поэтому нужно отдельное поле |
| поиск по slug не находит пост | на WP slug меняется при конфликте (`-2`), см. B1 и B2. Лучше искать по маркеру через `search=<pub-id>`: на настоящем WP это работает и для черновиков без slug |
| платформа без черновиков | README честно говорит, что нужен чистильщик. Но тогда гарантия деградирует до «дубль виден, пока его не снимут», и это стоит назвать прямо |
| статья вышла сразу, если черновик почему-то виден | Webflow: элемент со `isDraft: false` уходит live при публикации сайта клиентом. README это учитывает |
| переименование шагов адаптера | при rolling deploy старые воркеры получают `ValueError` на неизвестном шаге и жгут попытки. «Только добавлять шаги» тоже несовместимо со старыми воркерами в момент выкатки |
| сбой media-шага | поиска нет, поэтому после неясного таймаута файл в медиатеке остаётся лишним (это заявлено). Файл публично доступен по URL, но нигде не залинкован |
| зомби делает «идемпотентный» publish поздно | может повторно опубликовать пост, который клиент только что снял. Теоретически, одной строкой |

### 1.4 Таблица платформ: **частично неточна** (детали в разделе 3)

Shopify описан точно. В Webflow и Wix есть фактические ошибки.

### 1.5 Цифры: **в целом верны**

| утверждение | проверка |
|---|---|
| 200k/день = 2,3/с, пик ×10 ≈ 25/с | 2,31/с ✓ |
| 10 попыток ≈ 4 ч | задержки 30+60+120+240+480+960+1920+3600+3600+3600 = 14 610 с = **4,06 ч** в среднем (с jitter 2–6 ч) ✓. Статус `failed` ставится на 11-м pick |
| ~40k статей/день на сайт | 86 400 / 2 с = 43k при `rate_per_sec=2` и ответе ≤0,5 с ✓. При ответе за 1 с вдвое меньше |
| ~4 вызова платформы на статью ≈ 1M/день | 800k плюс ретраи ✓ |
| ~6 записей в БД на статью, ~150/с пик | pick + 3 checkpoint + аренда/освобождение ✓ |
| ~50 сайтов в полёте: **«one process»**, 3 для HA | по закону Литтла 50 ✓. Но `LANES` по умолчанию 20, а один процесс с 20 лейнами даёт около 10 статей/с. Нужно `LANES≥50` или «3 процесса × 20» |
| 70M строк в год, «monthly partitions» | 73M ✓. Но в Postgres ключ партиционирования обязан входить в `UNIQUE`, а `UNIQUE (article_id, destination_id)` его не содержит. Партиции по месяцу ломают идемпотентный enqueue. Архивация `done`-строк тоже снимает защиту от повторного enqueue старой статьи |

### 1.6 Чего не хватает и что лишнее

- **Оверинжиниринга нет.** Три таблицы и один цикл воркера — это минимум для такой задачи.
- **Не хватает для продакшена:**
  - продления аренды или проверки, что аренда ещё наша, перед вызовом;
  - общего дедлайна на запрос (`asyncio.timeout`);
  - `connect_timeout`, TCP keepalive и backoff при переподключении к БД;
  - обработки 503 с `Retry-After` как паузы всего сайта;
  - circuit breaker на сайт: сейчас лежащий сутки сайт клиента за 4 часа переводит **все** свои статьи в `failed`;
  - сверки фактического состояния перед тем, как ставить `failed` (баг B5);
  - нормализации идентичности сайта: один WP, подключённый дважды как `www` и без, даст две публикации.

## 2. Найденные баги

### B1. На WordPress лишний черновик занимает slug, и статья выходит по адресу `slug-2`. Серьёзность: средняя (для SEO-продукта неверный URL — это дефект продукта)

- **Где:** `platforms.py:88` создаёт черновик сразу с `slug`; README, строка 125 («worst case is a second draft, which never goes live»); глоссарий на русской странице («Лишний черновик безвреден»); рис. 3 на обеих страницах.
- **Механизм.**
  - Проверка уникальности slug при публикации в WP идёт по постам любого статуса, включая черновики ([wp_unique_post_slug](https://developer.wordpress.org/reference/functions/wp_unique_post_slug/): `WHERE post_name = %s AND post_type = %s AND ID != %d`, фильтра по статусу нет).
  - На WP 7.1.3 второй черновик с тем же явным slug через REST сразу получает `-2`.
  - Победитель CAS публикуется по тому адресу, который ему достался.
- **Воспроизведение:** `wp/adapter_real.py`, неизменённые `WordPress` и `run_steps` против настоящего WP, гонка зомби из `zombie_check`.
  ```
  2.0 outcome=['LostRace','dict'] live url=.../race-…-0-2/  posts: [(19,'publish','race-…-0-2'), (20,'draft','race-…-0')]
  … 5 из 5 гонок: live-статья на «-2», исходный slug держит невидимый черновик
  ```
  Тот же эффект при последовательном сценарии: ответ на create потерян, повторный поиск поста не увидел, создан второй черновик (`rest_checks.py`, пункты 2–4).
- **Почему тест не видит:** фейк вообще не моделирует уникальность slug.
- **Фикс (проверен на настоящем WP, `fix_checks.py`):**
  1. Создавать черновик без `slug`.
  2. Искать по маркеру: `GET /posts?search=<pub-id>&status=draft,publish&context=edit` находит черновики с маркером.
  3. На шаге publish отправить в корзину (trash) остальные черновики с нашим маркером, затем `{"status": "publish", "slug": slug}`. Результат: точный slug. Без trash даже явный slug даёт `-2`.
  4. Если вернувшийся slug не совпал с заданным, значит адрес занят собственным постом клиента (`rest_checks.py`, пункт 7, `taken-slug-2`). Сейчас это происходит молча; нужно предупредить клиента.

### B2. «БД восстановили из старого бэкапа» даёт дубль в 3 из 4 вариантов. Серьёзность: средняя (сценарий редкий, но прямо заявлен как защищённый)

- **Где:** README, строка 127; обе страницы, строки «DB restored from an old backup» и «базу восстановили из старого бэкапа».
- **Воспроизведение** (`wp/restore_real.py`, настоящий WP, неизменённый код):
  ```
  R1 restore, slug intact:           live posts with our marker: ['r1-…']                  ← заявление верно только здесь
  R2 restore after a zombie race:    before ['r2-…-2'] -> after ['r2-…', 'r2-…-2']           ← адоптирован лишний черновик с тем же маркером
  R3 restore, slug was taken:        before ['r3-…-2'] -> after ['r3-…-2', 'r3-…-3']         ← поиск по исходному slug не видит наш пост на «-2»
  R4 restore, row missing in backup: live posts of this article: ['r4-…', 'r4-…-2']          ← повторный enqueue выдал новый gen_random_uuid(), а значит новый маркер
  ```
- **Фикс.** R2 и R3 закрывает фикс B1: убрать лишние черновики до публикации и искать по маркеру, а не по slug. R4 закрывает детерминированный id публикации от стабильного ключа: `uuid5(article_uuid, destination_id)` или маркер `ryze:<article-uuid>:<site>`. Опираться на `bigserial` здесь опасно: после восстановления из бэкапа последовательность может выдать тот же id другой статье.

### B3. `Retry-After` в формате HTTP-date: попытки сгорают, сайт не ставится на паузу. Серьёзность: средняя

- **Где:** `platforms.py:52`, `float(r.headers.get("Retry-After", 30))`. RFC 9110 допускает и секунды, и дату.
- **Механизм.** `ValueError` вылетает не как `RateLimited`, а попадает в общий `except Exception` (`publisher.py:119`). Попытка засчитывается, сайт на паузу не встаёт, и лейна сразу берёт следующую статью и снова бьёт в сайт, который просил подождать.
- **Воспроизведение** (`repro_bugs.py`, пункт 1):
  ```
  Retry-After='120':                           site paused=True,  attempts=[0, 0, 0]
  Retry-After='Wed, 21 Oct 2026 07:28:00 GMT': site paused=False, attempts=[1, 1, 1], last_error='ValueError(...)'
  ```
- **Фикс.** Пробовать `float()`, иначе `email.utils.parsedate_to_datetime(...) - now`, иначе 30 с. Заодно 503 с `Retry-After` трактовать так же, как 429.

### B4. Гонка с переподключением: сайт с уже исправленными кредами снова уходит в `needs_reauth`. Серьёзность: низкая или средняя (клиенту придётся переподключаться дважды, будет тикет в поддержку)

- **Где:** `publisher.py:110`, `UPDATE destinations SET status = 'needs_reauth' WHERE id = %s` без условия на версию кредов.
- **Механизм.** Лейна держит снимок сайта со старыми кредами (до `SLICE` = 20 с, а у зомби дольше). Клиент в это время переподключает сайт. Лейна получает 401 и паркует уже исправленный сайт.
- **Воспроизведение** (`repro_bugs.py`, пункт 2): `site status='needs_reauth' although DB credentials are now 'secret'`.
- **Фикс.** Одно условие: `... WHERE id = %s AND credentials = %s` (старые креды из снимка) либо отдельная колонка `credentials_version`.

### B5. Статья live, а в БД стоит `failed`. Серьёзность: низкая

- **Механизм.**
  - Publish проходит, но ответ теряется. На WP так бывает часто: хуки публикации (кеш, соцсети, SEO-плагины) работают дольше 15 с.
  - После `MAX_ATTEMPTS` статья получает `failed`, и клиенту сообщают о сбое, хотя пост опубликован.
  - Вариант через зомби: `Fatal` у зомби ставит `failed`, пока новый владелец успешно публикует.
- **Воспроизведение** (`repro_bugs.py`, пункт 3): `platform says post 42 live=True, DB says 'failed'`.
- **Фикс.** Перед тем как ставить `failed` на шаге publish, сделать `GET` поста по `post_id` и, если он `publish`, закоммитить `done`. Re-drive уже сейчас чинит это безопасно.

### B6. Мелочи. Серьёзность: низкая

- **Ошибка CDN.** `media` скачивает картинку мимо `call()` (`platforms.py:73`). Ответ CDN 404 становится `HTTPStatusError`, его повторяют 10 раз за 4 часа, хотя это постоянная ошибка.
- **Переподключение к БД.** Лейна переподключается с фиксированной паузой в 1 с без jitter (`publisher.py:139`), нет `connect_timeout` и keepalive. При пропадании сети во время failover соединение может висеть, пока TCP не сдастся (минуты).
- **Ошибка конфигурации сайта.** Неизвестный `platform`, `rate_per_sec = 0` или кредов нет: исключение вылетает вне `try` в `serve()`, лейна падает, и сайт снова пробуется каждые 60 с. Попытки при этом не тратятся, но статус никто не выставляет.
- **Вечный 429.** Если сайт отвечает 429 всегда, его статьи никогда не уходят в `failed`, потому что попытки возвращаются. Заметит только алерт по возрасту очереди. Как решение это нормально, но стоит назвать.
- **Деплой и PgBouncer.** psycopg3 по умолчанию готовит prepared statements после 5 выполнений. С PgBouncer в transaction mode нужен `prepare_threshold=None` либо PgBouncer ≥1.21.

**Что проверил и где багов не нашёл.** `release` по равенству `lease_until`: точность в мкс сохраняется в обе стороны. REFUND без условия на `status`: безвреден. `EvalPlanQual` в LEASE_SITE и PICK при `SKIP LOCKED`: корректно. Graceful shutdown. Переподключение после `pg_terminate_backend`. asyncio: состояние лейн общим не является, pacing у каждой аренды свой.

### 6.2 Что осталось или появилось (воспроизведено на настоящем WP)

**N1. Статья со slug не из ASCII не публикуется никогда. Серьёзность: средняя. Было и до исправлений.**
- **Где:** `platforms.py`, шаг `media`, строка `filename="{pub["slug"]}.jpg"` в `Content-Disposition`.
- **Механизм.** httpx кодирует заголовки в ASCII: `UnicodeEncodeError`. Ошибка падает в общий `except Exception`, её повторяют до `MAX_ATTEMPTS`, и статья получает `failed`, так и не выйдя.
- **Воспроизведение** (`recheck_real.py`, slug `статья-…`). Строка в БД: `pending`, `last_error=UnicodeEncodeError('ascii', 'attachment; filename="статья-….jpg"', …)`.
- **Масштаб.** Кириллица, умлауты, `café`: любая статья с такими символами в slug.
- **Фикс (проверен).** `filename="{pub["article_uid"]}.jpg"`. С ним статья публикуется по адресу `/%d1%81%d1%82…/`.

**N2. Если на сайте отключена корзина, статья с лишним черновиком застревает навсегда. Серьёзность: средняя или низкая.**
- **Механизм.**
  - `EMPTY_TRASH_DAYS=0` — частый совет по оптимизации WP.
  - При такой настройке `DELETE /posts/{id}` без `force` возвращает `501 rest_trash_not_supported`. Это 5xx, то есть `Retry`.
  - Шаг publish спотыкается на этом каждый раз, а после `MAX_ATTEMPTS` статья получает `failed`.
- **Воспроизведение** (`recheck_notrash.py`: гонка зомби, затем 3 повтора).
  ```
  retry 0..2 Retry 501 {"code":"rest_trash_not_supported", …}
  db: {'status': 'pending', 'step': 'publish'} | posts: [(76, 'draft', ''), (77, 'draft', '')]
  ```
- **Фикс.** Черновики теперь создаются без slug, поэтому корзина нужна только для уборки. Ошибка при удалении не должна блокировать публикацию: `ok=(410, 501)` либо повтор с `?force=true` (это наш собственный лишний черновик).

**N3. При повторе публикации в корзину уходит копия клиента с нашим маркером. Серьёзность: низкая (нужен повтор публикации: восстановление или re-drive).**
- **Механизм.** Маркер копируется вместе с контентом, например через «Duplicate Post» или «Rewrite & Republish». `mine()` ищет по маркеру и не проверяет автора поста.
- **Воспроизведение** (`recheck_edges.py`, `recheck_pubcopy.py`).

  | креды сайта | черновик-копия клиента | опубликованная копия клиента |
  |---|---|---|
  | admin | `trash` | `trash`: страница клиента пропадает с сайта |
  | author | не тронута | не тронута, ложного `needs_reauth` нет (author просто не видит чужие посты) |

- **Фикс.** В `mine()` оставлять только посты, у которых `author` совпадает с нашим пользователем (`GET /wp/v2/users/me` один раз на аренду). И никогда не отправлять в корзину посты со статусом `publish`.

**N4. Ложный warning «slug занят» для slug не из ASCII. Серьёзность: низкая.**
- **Механизм.** После фикса N1 WP возвращает slug в percent-encoding (`%d1%81…`). Сравнение `state["slug"] != pub["slug"]` всегда срабатывает, и клиент видит warning при верном адресе.
- **Воспроизведение:** `recheck_edges.py`.
- **Фикс.** Сравнивать `urllib.parse.unquote(state["slug"])`.

**N5. Поиск по маркеру зависит от того, что поиск WP не подменён плагином. Серьёзность: низкая. Не проверено.**
- `mine()` полагается на штатный `search=` (LIKE по `post_content`).
- ElasticPress, Relevanssi и SearchWP могут перехватывать поиск в REST: тогда индекс может отставать или вырезать HTML-комментарии.
- Основной путь всё равно защищён CAS. Сломается подхват поста при восстановлении из бэкапа (R1–R4), и вернутся дубли.
- **Подстраховка.** Объединять с поиском опубликованного поста по `slug`, как было раньше.

**N6. Повтор публикации сбрасывает slug, который клиент сменил вручную. Серьёзность: низкая. Выведено из кода, не прогонялось.** `publish()` всегда отправляет `slug`. Если после публикации клиент сам сменил slug нашей статьи, повтор публикации (восстановление, re-drive или поздний зомби) вернёт исходный адрес.

**Что сделать до сдачи:** N1 (одна строка) и N2 (один кортеж). Оба бага означают «статья не вышла» на реальных сайтах. N3–N6 и B5 можно назвать как trade-off.
