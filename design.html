System design review · working demo included

Exactly-Once Publisher

200,000 SEO articles a day go to customers' Shopify, WordPress, Webflow and Wix sites. Any call can fail or time out, and the service can die at any moment. Every article must end up live exactly once.

No platform takes an idempotency key for posts, so we guarantee an exactly-once effect: calls may repeat, and repeats are harmless. The load is small (2.3 articles/s average, ~25/s at peak, ~50 sites in flight). One Postgres and a few stateless workers handle it.

Postgres is the queue

One row is the job, its state and its lock. Nothing else to keep in sync.

Lease the site

Lease what the platform rate-limits, usually the site. One worker owns it at a time.

Draft, find, commit, publish

Nothing is visible until an idempotent final step, applied to the one id in the DB.

Architecture

  1. Lease a site: the least recently served one with work due, via SKIP LOCKED.
  2. Pick an article and push its run_at out by the backoff before working on it. A crash then retries it on its own.
  3. Run the steps (media → draft → publish), committing after each step with WHERE step = current.
  4. Release the site after 20 s. On a 429 or 503, release it until Retry-After (seconds or a date).

One article, with a lost response

Why it holds

Invariant. Publish, the only action readers see, is applied only to the post id stored in Postgres, and Postgres accepts one id per publication. Leases only affect speed, never correctness.

Failures and edge cases

situationbehaviour
timeout · 5xxretry with backoff + jitter, 30 s up to 1 h. After 10 attempts (~4 h): failed + alert
429 · 503the whole site backs off for Retry-After (seconds or HTTP-date); the attempt is refunded
401 / 403refresh the token once. If that fails and the credentials haven't changed meanwhile, the site goes to needs_reauth and its articles wait without using attempts
permanent 4xxfailed right away, with the platform's message for the customer
kill -9 / deploythe lease expires, and work resumes from the last committed step. SIGTERM finishes the current article first
poison articleattempts count up at pick time, so it ends up failed instead of looping
slug taken by the customertheir post is never adopted (no marker). Ours goes live as slug-2 with a warning
clock skewall time comparisons use Postgres now()

One adapter class per platform, all under the same contract. Only WordPress is built in the demo. The others were checked against the platforms' docs, and still need a check against the pinned API versions.

Stack

Use

  • Managed Postgres (RDS, Cloud SQL)
  • Stateless workers on ECS or K8s, autoscaled on the oldest due article
  • KMS for tokens · OpenTelemetry, Grafana, Sentry

Not used, on purpose

  • Kafka, SQS: a dual write, at ~2 msgs/s
  • Redis limiter: the site lease covers it
  • Temporal: the non-idempotent create stays ours anyway

The working version

chaos.py runs 500 articles to 20 sites, with the enqueue run twice. Every 1–3 s it SIGKILLs a worker or freezes one past its lease. The fake platform fails 10% of calls (before or after doing the work, or by hanging), rate-limits, lags its search, and follows WordPress's slug rules. Every 10th slug is Cyrillic. Then it forces the Fig. 3 race and replays an article after a DB restore, on a site with the trash disabled.

OK: every article is live exactly once, at its own slug

The check can fail. Without the step guard the zombie publishes twice, drafts that carry a slug go live as slug-2, a marker built from the publication id duplicates after a restore, a slug in the media filename stops Cyrillic articles, and a disabled trash blocks publishing. An independent review (REVIEW.md) found the last four on a real WordPress, and they are fixed.

Scaling path: at 10× it's still one Postgres (PgBouncer, partitions). At 100×, shard by site. An app-wide quota means adding a Redis bucket. A platform without drafts needs a sweeper that unpublishes duplicates.
